About

This is a private speed test. You can use it to check the speed and consistency of your connection, verify what your provider actually delivers, compare networks, or test connectivity in different parts of a building.

Everything you measure here is measured against a test worker on this deployment. There is no third-party network in the path, and no result leaves the machine.

FAQs

Why run another speed test tool?

Public speed tests measure your connection to one specific provider's network. Running your own instance means you measure the path you actually care about: from your browser to a machine you control. It also means the tool keeps working when the Internet is degraded, which is exactly when you want to measure it.

How did you build this tool?

The front end is a static page: HTML, CSS and a single JavaScript file. The server is a small Node application with no dependencies at all.

Measurements do not run inside that application. The application talks to the Docker daemon through the mounted socket and starts short-lived test worker containers on demand, on a private Docker network. Each browser session is pinned to one worker, and workers are removed again after a period of inactivity.

Because the workers publish no ports and the browser only ever talks to the application, the page stays same-origin and exactly one port is exposed. Download and upload traffic is piped straight through to the worker without being buffered, so the numbers describe the wire, not the application's memory.

What does a test worker do?

A worker is a tiny HTTP server with four jobs:

  • /__speed/ping answers a small, uncached request, used for latency probes.
  • /__speed/down?bytes=N streams N bytes of incompressible data from a preallocated buffer, honouring backpressure, up to a configured cap.
  • /__speed/up reads the request body and counts it, without storing anything.
  • /__speed/meta reports the worker label so the page can show where it is testing.

Nothing is written to disk and no measurement is recorded. Worker containers run read-only, with all capabilities dropped, a memory limit, a CPU limit and a process limit.

How does it work?

Latency is the median of 20 sequential probes, each timed from request to complete response. Jitter is the average absolute difference between consecutive probes. Packet loss is the share of those probes that failed — it is measured with HTTP requests, not UDP, so it reflects loss as your browser and this server experience it.

Download and upload each run four parallel streams for an eight-second window. Throughput is sampled every 200 ms, the first 700 ms are discarded as warm-up, and the reported figure is the 90th percentile of the remaining samples. That keeps a single slow request from dragging the result down while ignoring startup ramp-up.

Loaded latency is measured by firing a small probe every 500 ms while the download and the upload windows run, so you can see how the connection behaves under load instead of only when idle.

The Network Quality Score turns those numbers into three grades: streaming from download speed, loaded download latency and loss; gaming from idle latency, jitter and loss; and video calls from upload speed, loaded upload latency, jitter and loss.

Do you collect any data?

No. There is no analytics script, no external font or image request, and no result is stored on the server. The page fetches its own files and the measurement endpoints, and that is all. Worker containers and their bookkeeping live in memory for as long as they exist, and disappear with them.

How can I improve my speed?

Test at different times of day and from a wired connection to separate local Wi-Fi problems from the line itself. Move closer to the access point, use the 5 GHz or 6 GHz band when available, close background transfers, and check whether a VPN or a busy router is adding latency. If download is fast but loaded latency is high, the issue is usually buffering in the router or modem.

Why are my results different than other speed tests?

Two reasons. First, the destination: a server on your own network, in your own building, is a shorter path than a public speed test's nearest data centre. Second, the method: how long a test runs, how many streams it uses, and whether it reports an average, a peak or a percentile all change the number you see.

This tool reports the 90th percentile of sampled throughput over an eight-second window with four parallel streams, and it names every figure it shows, so you can compare it fairly with anything else you use.

What is the map showing?

The map is a static illustration, not a geolocation lookup. The test server name in the sidebar comes from the WORKER_LOCATION setting of this deployment, and the address shown is the one this server sees for your browser. Nothing about your location is looked up or sent anywhere.
